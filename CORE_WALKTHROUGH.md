# From separate neurons to a connected network

The previous stage stored several neurons' voltages and updated each neuron
using a current supplied by the testbench. This stage adds the connections
between neurons. An incoming spike now selects stored connection weights;
those weights become the currents that update the neurons. Output spikes
are remembered and become inputs to the next network step.

The integrated module is `rtl/lif_snn_core.v`. It connects the synapse router
to the population stepper. The example below uses the actual configuration
and weights generated by `tools/run_snn_core_check.py`.

The trained-image stage is now available separately in
[MNIST_RTL_VERIFICATION.md](MNIST_RTL_VERIFICATION.md). This walkthrough
continues to explain the four-neuron ring regression.

## Think of four buckets connected by signals

Each neuron has its own bucket of charge, called its membrane voltage.
Adding current fills the bucket; negative current removes charge. Leakage
removes some charge before the current is added. When the voltage reaches
the threshold, the neuron sends a spike and returns to its reset voltage.

A spike is an event, not the voltage itself. A connection weight says how
much current that event contributes to another neuron. A weight of `+7`
means “add 7 units to this destination when this source spikes.” A weight
of `-2` means “subtract 2 units.” A weight of zero contributes nothing.

The four-neuron demonstration connects the neurons in a ring:

```text
N0 --(+7)--> N1 --(+7)--> N2 --(+7)--> N3 --(+7)--> N0
```

Every other connection has weight zero. These are deliberately chosen test
weights, not weights learned from MNIST.

| Setting | Value | Meaning |
|---|---:|---|
| Threshold | 8 | Fire when the updated voltage reaches at least 8 |
| Reset voltage | 3 | Starting voltage and voltage immediately after firing |
| Leak shift | 2 | Subtract the current voltage shifted right by 2 |
| Refractory period | 2 | Ignore current for the next two network steps after firing |

For a neuron that is ready to process input, the calculation is:

```text
leak = old_voltage >> 2
candidate = old_voltage - leak + input_current
```

The right shift uses integer arithmetic. For example, `3 >> 2` is `0`,
while `10 >> 2` is `2`. A neuron at voltage 3 therefore loses no charge
with this configuration. Negative candidates clamp to zero. A threshold
crossing generates a spike, sets voltage to 3, and loads refractory count 2.

## The first complete network step

Initially all four voltages are 3, all refractory counters are zero, and
there are no remembered output spikes.

The testbench injects one external event at source N0. In the waveform this
is `input_spikes = 0001`. Binary values here are written in the order
`N3 N2 N1 N0`, so the rightmost bit belongs to N0.

1. The testbench pulses `step_start` while the core is idle.
2. The router captures the source bitmap. Only N0 is active.
3. It calculates a current for each destination from the stored weights.
   N0 connects only to N1, so the destination currents are `[0, 7, 0, 0]`
   in N0-to-N3 order.
4. The router presents each destination current with `current_valid`. The
   population stepper stores each current in that destination's slot.
5. Once routing finishes, the core starts the population update. One shared
   LIF calculation unit visits N0, N1, N2, and N3 in order, using three
   clocks per neuron: registered read, calculation, then state write.
6. The finished spike bitmap is returned, and its events are remembered
   for the following network step.

For N1, the calculation is `3 - (3 >> 2) + 7 = 10`. Since `10 >= 8`,
N1 fires. Its voltage becomes 3 and its refractory counter becomes 2.
The extra voltage above the threshold is discarded.

For each other neuron, the calculation is `3 - 0 + 0 = 3`. It does not
fire and its refractory counter stays zero.

The first completed result is therefore:

```text
spike_vector = 0010       (N1 fired)
voltages     = [3, 3, 3, 3]
refractory   = [0, 2, 0, 0]
```

All voltages being 3 does not mean nothing happened. N1's spike and
refractory count show its threshold crossing and reset.

## What happens on the next steps

After the first step, the external input is zero for the rest of the test.
The network continues because it remembers its own output spikes.

On step 2, remembered N1 selects the `N1 -> N2` connection. N2 receives
7 units and fires. Meanwhile N1 is refractory: it ignores current, holds
voltage 3, and reduces its counter from 2 to 1.

On step 3, N2's remembered spike makes N3 fire. N1's refractory counter
goes from 1 to 0. It becomes eligible to process current on step 4.

On step 4, N3 makes N0 fire, closing the ring. On step 5, N0 makes N1
fire again. N1 has completed its two blocked steps by then.

| Completed step | External source | Remembered source used | Neuron firing | Output bitmap | Refractory counters N0–N3 |
|---|---|---|---|---|---|
| 1 | N0 | None | N1 | `0010` | `[0, 2, 0, 0]` |
| 2 | None | N1 | N2 | `0100` | `[0, 1, 2, 0]` |
| 3 | None | N2 | N3 | `1000` | `[0, 0, 1, 2]` |
| 4 | None | N3 | N0 | `0001` | `[2, 0, 0, 1]` |
| 5 | None | N0 | N1 | `0010` | `[1, 2, 0, 0]` |

All four voltages remain 3 in these rows. The spike moves one connection
per **network step**. A network step takes several FPGA clocks because
the core first routes currents and then updates the neurons sequentially.
It is not one neuron per vector row: every row updates all four neurons.

## Which file does each job?

| File | Job |
|---|---|
| `rtl/lif_synapse_router.v` | Stores signed 4-bit weights, captures source spikes, and produces destination currents |
| `rtl/lif_population_stepper.v` | Stores each neuron's voltage/counter/current and updates one neuron per three clocks |
| `rtl/lif_transition.v` | Calculates leak, current addition, threshold, reset, and refractory behavior |
| `rtl/lif_snn_core.v` | Starts routing, waits for currents, starts neuron updates, and remembers output spikes |
| `golden_model/network.py` | Python reference for routing and recurrent network steps |
| `tools/run_snn_core_check.py` | Builds the ring and expected Python results, then compiles and runs RTL |
| `rtl/tb/lif_snn_core_tb.v` | Loads the weights/inputs and compares RTL spikes and all neuron states against Python |

The router now scans source addresses and reads one active-source weight
synchronously before adding it. This schedule supports BRAM inference;
destination currents arrive with `current_valid` and variable spacing.
The ring's numerical results are unchanged, but routing takes more clocks
than the earlier combinational implementation. Use the current waveform
instead of timings from the earlier design.

## Run and inspect the demonstration

From `D:\RTL_PROJECT` in PowerShell:

```powershell
python -m tools.run_snn_core_check --neurons 4 --transactions 24
```

The expected success message is:

```text
PASS: matched Python SNN model for 24 transactions (4 neurons)
```

The runner writes weights, readable text vectors, packed hex vectors, and
the small-run VCD under `build/lif_snn_core/`. The text vectors begin with
external source addresses followed by a `-1` separator. The remaining
fields are configuration, input bitmap words, expected output bitmap
words, voltages, and refractory counters. The hex file packs these fields
for the testbench; it contains the same reference data without the address
list and separator.

In Vivado, use simulation top `lif_snn_core_tb` and run `run all`.
Generate the four-neuron vectors first. Both sizes use the same filenames,
so a 256-neuron run must finish before regenerating four-neuron files.

Useful waveform signals are:

| Signal | What to look for |
|---|---|
| `clk`, `rst` | Clock and initial reset |
| `step_start`, `input_spikes` | Step request and external events |
| `dut.core_state` | 0 idle, 1 routing, 2 launch population, 3 updating/waiting |
| `dut.synapse_router.active_sources` | Captured external/remembered source bitmap |
| `dut.route_current_valid`, `dut.route_destination`, `dut.route_current` | Each destination current being delivered |
| `dut.population_stepper.neuron_index` | Which neuron the shared update unit is visiting |
| `busy`, `done` | Work in progress and population completion pulse |
| `spike_vector`, `expected_spikes` | Actual and Python expected outputs; compare at completion |
| `state_read_addr`, `state_read_membrane`, `state_read_refractory` | Readback of each neuron's stored state |

The testbench prepares inputs on falling clock edges. RTL registers capture
and update on rising edges. `spike_vector` is built during the population
scan, so inspect its complete value at `done`. Wait for `busy` to clear
before issuing another step; the core captures feedback on the clock
after the population's completion pulse.

## What this demonstration establishes

The test checks that stored weights turn events into currents, currents
update persistent neuron state, and resulting spikes propagate on the next
step. Every completed step checks the full output bitmap and each neuron's
voltage and refractory counter against Python.

This ring demonstrates recurrent propagation. It does not establish MNIST
RTL accuracy, serial AER fairness, processor/DMA/UART integration, or FPGA
timing/resource results. The separate trained-image test now maps the
software MNIST example to exactly 256 states with outputs at 246..255;
see its verification guide for the mapping and tested accuracy.

The core combines external and recurrent events using bitmap OR. The ring
test avoids overlapping external/recurrent sources; repeated events at one
address are not separately represented by that interface. Python's event
list can count such duplicates separately, so that case needs an agreed
contract and additional verification before wider integration.
